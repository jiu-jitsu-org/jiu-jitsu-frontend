# 네이티브 알럿·바텀시트 브릿지

> **상태: 웹 구현 완료 / 네이티브 미구현.**
> 메시지 계약은 `src/shared/lib/native-bridge/messages.ts`에 반영됐고, 웹은 이 계약으로 요청을 보냅니다.
> 다만 **앱에는 아직 수신부가 없어** 실기기에서는 웹 폴백이 아니라 **무응답 → 취소**로 처리됩니다
> (네이티브 배포 전까지 앱에서 알럿이 뜨지 않음). 브라우저 단독 실행은 웹 폴백으로 정상 동작합니다.

커뮤니티 게시글 ⋮ 메뉴(삭제/신고/숨기기/수정)의 확인 알럿과 신고 바텀시트를
**네이티브가 그리고, API는 웹이 계속 태우는** 방식으로 정리한 내용입니다.

---

## 1. 왜 필요한가

앱 화면은 세로로 `GNB - 웹뷰 - 하단 탭바` 구조입니다.
지금 알럿은 웹뷰 안의 DOM(`ConfirmDialog`)이라 **딤이 가운데 웹뷰에만** 걸립니다.
디자인 요구는 **GNB·탭바까지 덮는 풀스크린 딤**입니다.

웹뷰는 자기 프레임 밖을 그릴 수 없습니다. GNB/탭바를 덮는 딤은 **네이티브만 소유 가능한 표면**이라,
이건 취향 문제가 아니라 구조적 제약입니다.

### 적용 범위: 메인 피드 리스트만

게시글 **상세**는 `OPEN_SUBVIEW`로 네이티브가 풀스크린 웹뷰를 push하는 구조라
(`use-open-post-detail.ts`) 상세 앱바 ⋮의 알럿은 이미 화면 전체가 덮입니다.

> ⚠️ 상세 서브뷰가 실제로 GNB까지 덮는지는 iOS와 한 번 확인 필요.

즉 고칠 대상은 **메인 피드 카드의 ⋮ 알럿**입니다.

## 2. 결론

| 영역 | 소유 |
|---|---|
| 풀스크린 딤 · 알럿 셸 · 바텀시트 셸 | **네이티브** |
| 문구 · 버튼 라벨 · 정책 분기 · API 호출 · 리스트 반영 | **웹** |

한 줄 요약: **웹 = 무엇을 물어보고 확인 후 뭘 할지 / 네이티브 = 어떻게 보여주고 어느 버튼이 눌렸는지 회신.**

---

## 3. API는 왜 웹이 태우나

네이티브도 토큰이 있어 호출 자체는 가능합니다. 하지만 **어차피 웹으로 돌아와야 합니다.**
리스트 상태(어떤 글이 몇 개 떠 있는지)는 웹뷰 메모리(`useBoardFeed`)에 있어서,
네이티브가 삭제를 성공시켜도 "카드 지워라"를 웹에 알려야 합니다. **왕복 횟수는 어느 쪽이 호출하든 동일합니다.**

그럼 남는 건 비용 비교입니다.

| | 웹이 호출 (채택) | 네이티브가 호출 |
|---|---|---|
| 엔드포인트·에러 처리 | 이미 있음 (BFF `app/api/community/*`) | iOS/Android가 각각 다시 구현 |
| 409 중복 신고 문구 | 웹 배포로 수정 | 앱 심사 대기 |
| 신고 사유 목록 변경 | 웹 배포로 수정 | 앱 배포 |
| 왕복 | 1회 | 1회 (동일) |

## 4. 브릿지 계약

새로 필요한 건 **2쌍**입니다. 수정하기는 기존 메시지를 재사용해 **신규 0개**입니다.

| 흐름 | 메시지 |
|---|---|
| 확인 알럿 | `SHOW_CONFIRM_DIALOG` ↔ `CONFIRM_DIALOG_RESULT` |
| 선택 바텀시트 | `SHOW_SELECT_SHEET` ↔ `SELECT_SHEET_RESULT` |
| 수정 화면 이동 | 기존 `OPEN_SUBVIEW` |

### requestId — 이 계약의 유일한 신규 개념

현재 브릿지는 **전부 단방향(fire-and-forget)** 이고 요청↔응답을 짝지어 주는 수단이 없습니다.
알럿은 "확인이 눌렸는지"를 받아야 하므로, 요청마다 **주문번호**를 붙입니다.
(카페 진동벨과 같습니다. 모르는 번호가 오면 무시합니다.)

```
웹 →  { requestId: "r1", title: "게시글 삭제", ... }
웹 ←  { requestId: "r1", result: "confirm" }
```

### 4-1. 확인 알럿

**웹 → 네이티브 `SHOW_CONFIRM_DIALOG`**

```ts
{
  requestId: string;              // 웹 발급, 응답 매칭용
  title: string;
  message?: string;
  confirmText: string;
  cancelText?: string;            // 기본 "취소"
  destructive?: boolean;          // true면 확인 버튼 빨강
  dismissOnOutsideTap?: boolean;  // 기본 true (바깥 탭 = 취소)
}
```

**네이티브 → 웹 `CONFIRM_DIALOG_RESULT`**

```ts
{
  requestId: string;
  result: "confirm" | "cancel" | "dismiss";  // dismiss = 바깥 탭/시스템 닫힘
}
```

### 4-2. 선택 바텀시트

신고 전용으로 만들지 않고 **범용 선택 시트**로 둡니다. 사유 목록을 웹이 넘기므로 항목이 늘어도 앱을 안 건드립니다.

**웹 → 네이티브 `SHOW_SELECT_SHEET`**

```ts
{
  requestId: string;
  title: string;
  message?: string;               // 제목 아래 보조 설명
  options: {
    value: string;                // API로 보낼 코드
    label: string;
    allowsCustomText?: boolean;   // 이 항목을 고르면 자유 입력 필드 노출("기타")
  }[];
  customTextPlaceholder?: string;
  submitText: string;
}
```

신고 시트 실제 값 (`REPORT_REASONS`, `domain/report.ts`):

| value | label |
|---|---|
| `ABUSE` | 욕설 및 비방 |
| `SPAM` | 광고 및 홍보 |
| `ADULT` | 음란 또는 부적절한 콘텐츠 |
| `INCITEMENT` | 분쟁유도 |
| `HARASSMENT` | 혐오 및 괴롭힘 |
| `OTHER` | 기타 (자유 입력) |

제목 "어떤 문제인가요?" / 설명 "신고는 익명으로 처리되며, 검토 후 조치돼요." / 버튼 "신고하기"
/ 입력 placeholder "신고할 내용을 입력해주세요."

**네이티브 → 웹 `SELECT_SHEET_RESULT`**

```ts
{
  requestId: string;
  result: "submit" | "dismiss";
  value?: string;                 // submit일 때 선택된 option.value (항상 채움)
  customText?: string;            // allowsCustomText 항목을 골라 입력했을 때만
}
```

> ⚠️ **`customText`는 현재 서버로 전달되지 않습니다.** `POST /reports` 요청 스키마가
> `reportType` / `targetId` / `reason` 3개뿐이라 상세 내용을 실을 필드가 없습니다.
> "기타"를 고르면 `reason: "OTHER"`만 전송되고 입력 내용은 버려집니다. 백엔드에 상세 필드가
> 추가되면 함께 싣습니다. (`domain/report.ts`의 `FIXME(계약)`)

### 4-3. 디자인은 왜 두 벌이 안 되나

문구·라벨을 **웹이 payload로 실어 보냅니다.** 네이티브는 빈 껍데기(딤 + 컨테이너 + 버튼)만 갖습니다.

- 껍데기는 iOS가 **한 번만** 구현 — 현재 웹 `ConfirmDialog` 수치를 그대로 전달
  (폭 `min(320, 화면폭−55)`, radius 20, 내부 여백 20, 버튼 높이 51 / radius 15, destructive `#E52012`, 페이드 200ms)
- 문구 변경은 **웹 배포만으로** 끝 → 앱 심사에 묶이지 않음
- 신고·차단 알럿을 나중에 추가해도 iOS는 손대지 않음
- 앱에서 보이는 알럿은 **항상 네이티브 것 하나** (두 벌이 동시에 뜨는 경우 없음)

웹 `ConfirmDialog`는 **앱 밖(브라우저 개발/데모)에서만** 쓰는 폴백으로 남습니다.

## 5. 흐름

### 삭제하기

```
웹  카드 ⋮ → 삭제하기
웹 → 네  "게시글 삭제 / 삭제한 게시글은 복구할 수 없어요 / [취소][삭제(빨강)]"
네       풀스크린 딤 + 알럿
네 → 웹  confirm
웹       DELETE /api/community/posts/{id}
웹       성공 → 토스트 + 리스트에서 카드 제거 (removePost)
         실패 → 토스트만 (카드 유지)
```

### 신고하기 (알럿 → 시트, 2단)

```
웹  카드 ⋮ → 신고하기
웹 → 네  "게시글 신고 / 신고된 게시글은 검토 후 처리돼요 / [취소][신고]"
네 → 웹  confirm
웹 → 네  선택 시트 "어떤 문제인가요?" (사유 6종 + 기타 자유 입력)
네 → 웹  submit + 선택한 사유 코드
웹       POST /api/community/reports  { reportType: "BOARD", targetId, reason }
웹       성공 → 토스트 + 카드 제거
         409  → "이미 신고한 게시글이에요" + 카드 제거
```

피드 카드와 상세 앱바가 **같은 훅(`useReportFlow`)** 을 쓴다 — 같은 글인데 진입 지점에 따라
문구·사유 목록이 달라지면 안 되기 때문.

> 409(이미 신고함)에도 카드를 지우는 이유: 이미 신고한 글이 목록에 계속 보이는 게 더 어색합니다.

> ❓ **디자인 확인 필요** — 사유 선택 자체가 확인 단계라, 알럿 없이 **바로 시트**로 가는 1단 구성도 가능합니다.
> **현재는 위 2단으로 구현**돼 있습니다. 1단으로 바꾸려면 `FeedCardMenu.handleReport()`에서
> `confirm(...)` 호출만 지우면 됩니다(시트·API는 그대로).

### 숨기기

**알럿 없음.** 확인 단계 대신 되돌리기 토스트로 취소 기회를 준다 — 되돌릴 수 있는 동작이라
매번 묻는 편이 더 번거롭다.

```
웹  카드 ⋮ → 숨기기
웹       POST /api/community/posts/{id}/hide   (업스트림 PUT /board/hide/{id})
웹       성공 → 카드 제거 + 토스트 "게시글을 숨겼습니다" [되돌리기]
웹  되돌리기 탭 → 같은 엔드포인트 재호출(토글이라 숨김 해제) → 카드를 원래 자리에 복원
```

- 업스트림이 **토글**이라 숨기기와 되돌리기가 같은 호출이다(별도 unhide 엔드포인트 없음).
- 복원은 맨 뒤가 아니라 **걷어냈던 인덱스**에 다시 끼운다(`restorePost`) — 시간순 피드에서 글이
  엉뚱한 자리로 튀지 않게.
- 되돌리기가 실패하면 카드는 숨겨진 채로 두고 실패만 알린다(서버와 화면이 어긋나는 편보다 낫다).
- 토스트는 액션이 있으면 5초간 노출한다(기본 2초로는 읽고 누르기 어렵다).

> ⚠️ **상세 화면의 숨기기는 아직 미연결입니다.** 상세에서 숨기면 그 화면을 닫아야 하는데, 닫고 나면
> 되돌리기 토스트를 띄울 자리가 없습니다. 동작 정의가 필요합니다.

### 수정하기

```
웹 → 네  OPEN_SUBVIEW { url: "/community/{id}/edit" }   ← 기존 메시지 재사용
```

알럿도 새 브릿지도 필요 없습니다. ⚠️ 수정 화면 웹 라우트(`/edit`)가 아직 없습니다.

## 6. 공통 규칙

- 삭제·신고·숨기기 셋 다 성공하면 결국 **`removePost(id)` 하나**로 끝납니다. 사라지는 이유만 다르고 처리는 같습니다.
- **낙관적 처리 안 함** — 서버 성공을 확인한 뒤 지웁니다. 카드가 사라졌다 되살아나면 안 됩니다.
- 모르는 `requestId` 응답은 **조용히 무시** (중복 회신 방어).
- **응답이 일정 시간 없으면 `cancel`로 간주** — 새 메시지를 모르는 구버전 앱에서도 화면이 멈추지 않게 하는 안전망.
- 알럿/시트가 떠 있을 때 `BACK_PRESSED` → **그것만 닫고 `dismiss` 회신**, 화면은 유지.
- 동시 요청이 오면 네이티브는 **1개만 표시하고 나머지는 즉시 `dismiss` 회신** (큐잉하지 않음).
- 앱 밖(브라우저)에서는 기존 웹 UI로 폴백 → `npm run dev` 개발이 계속 굴러갑니다.

## 7. 남은 결정 사항

| # | 항목 | 막히면 |
|---|---|---|
| 1 | 수정 화면 라우트 `/community/{id}/edit` + 수정 후 리스트 갱신 방법 | 수정하기 탭 시 404 |
| 2 | "기타" 자유 입력을 실을 요청 필드 (현재 스키마에 없음) | 사용자가 쓴 신고 내용이 버려짐 |
| 3 | 상세 화면에서 숨기기 했을 때 동작(화면 닫기 vs 유지, 되돌리기 위치) | 상세 숨기기 미연결 |
| 4 | `PUT /board/hide/{id}` 응답이 봉투 형식인지 raw `true`인지 | 현재 양쪽 모두 파싱하도록 방어 |
| 5 | 상세 서브뷰가 GNB까지 덮는지 확인 | 상세도 대상에 포함될 수 있음 |

~~신고 사유 코드~~ · ~~신고 2단/1단~~ · ~~숨기기 API~~ — 확정됨.

**1·2번이 막혀도 삭제·신고는 먼저 붙일 수 있습니다.** 숨기기/수정은 메뉴에 두되 지금처럼 미구현으로 남깁니다.
